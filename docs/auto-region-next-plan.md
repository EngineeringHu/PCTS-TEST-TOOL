# 轻量自动框选方案（待下次开发）

状态：仅记录方案，暂不实施。2026-11-19按用户要求撤回0.7.0自动框选代码，当前恢复0.6.1手工框选。

## 为什么撤回

0.7.0先逐帧扫描整段视频，再做约32～49次全图OCR和约12～27次手部识别。用户本次1920×1080、4299帧视频耗时292.463秒；日志只有总时长，不能准确分摊各阶段耗时。

实际画面暴露了定位问题：灯光首选落在车机下沿反光，真实手机闪光灯位于第二候选；MD/TX框包含部分PRESS HERE；触摸包络包含大量文字和彩色背景。多次检测到相同信号、能生成四个框或跑出10轮，均不能作为框选准确性的验收依据。

## 下次采用的流程

1. **从当前清晰帧开始。** 用户可以先定位到PRESS HERE与MD/TX可见的画面，再点击辅助框选；有必要时分开选择文字清晰帧和手指接近帧。
2. **文字两区自动定位。** 先对当前原帧做一次OCR，按标签分别生成PRESS HERE和MD/TX四边形。仅在缺失或不确定时补查少量原帧；建议首版总预算最多5帧，找到足够依据即停止，不转为全片搜索。采用清晰参考帧的框做局部边缘调整，避免直接将跨帧四角坐标取中位数后大幅扩框；两个文字区不能互相吞入。
3. **灯光区提供单点辅助。** 用户点一下真实光源，工具在该点附近按局部亮度/边缘生成小框，用户可拖角微调。亮度变化强、与灯同步的反光不能自动视为正确光源。单帧不足时明确提示换帧或局部调整，不再为找位置扫描全部闪烁周期。
4. **触摸区提供单点辅助。** 用户在清晰接近/接触画面点一下实际落点或指腹附近，工具生成覆盖局部指腹及接近空间的初始框，尺寸和角点可调整。不以PRESS HERE中心附近的肤色包络代替真实落点，不要求画参考线。
5. **确认后应用。** 用户核对四区，未找到的可手工补选。取消保留原任务；应用有变化的选区才按现有规则清空旧分析结果。完整视频的时序处理留给后续正式分析。

这是“文字自动定位＋灯光/触摸单点辅助”的方向，不承诺无需操作的全自动定位。若下次希望两个非文字区域也完全自动，需要另行说明可靠的语义/几何依据并用实际录像验证，不能回到全片盲搜或仅按闪烁强度排序。

## 开发边界

- 复用现有本地OCR/OpenCV；暂不引入大模型、训练流程或新依赖。
- 不改识别、计时、逐帧复核、手工框选、Excel导出及任务格式。
- 不使用历史视频坐标或人工表格作为运行模板。
- 无法可靠定位时保留缺失或请求一个点，不强凑四个框。
- 不能从用户点选位置推断“这就是press帧”；位置设置和事件定位分开。
- 优先复用当前帧/现有浏览缓存，限制补帧次数；框选阶段不进行全片解码。

## 下次验收重点

- 在用户实际Windows环境记录解码、OCR、局部定位与总耗时，以及实际读取/推理帧数；实现前不承诺“几秒完成”。
- 对照不同机位和背景的实际录像，分别检查真实光源/反光、两行文字分离、触摸局部范围；记录需要多少次修正、总操作时间是否少于手工框选。
- 检查四点角度、像素坐标、取消/应用、已有结果保留、显示模式与逐帧操作；测量帧号和数值不能因辅助框选过程被写入。
- 先验证上述少量关键路径和实片效果，再决定是否继续扩展。测试通过数不能替代实际定位精度和使用耗时。
